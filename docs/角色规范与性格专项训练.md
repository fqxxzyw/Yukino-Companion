# 角色规范与性格专项训练

版本：桌面端 0.4.0；角色包版本由 `characters/yukino/manifest.json` 管理。

这次实现两个可分别使用的部分：随 EXE 提供的完整统一的角色规范，以及独立文本模型的性格专项训练流程。API 模式加载角色规范即可使用，不要求用户先训练模型；本地模型微调属于另一个步骤。语音音色、3D / Live2D 不参与本次文字人格定义。

## 1. 角色规范保存了什么

完整文档在 [CHARACTER.md](../characters/yukino/CHARACTER.md)。它先记录姓名、生日、血型、年龄所对应的故事时间、学校与班级、家庭、生活、外貌、兴趣、能力、缺点、性格、人物关系和具体经历，再保留详细的对话行为指导与全部原创情境正反例。按最新确认，助手行为指导不删减；仅移除版本、用途及解释性前言。

用户最终要求是写完整人格，不划分前中后期模式。规范综合人物不同经历中体现出的认真、自尊、判断力、尖锐、关心、脆弱，以及信任、求助、表达需要、承担责任和自主选择方面的矛盾与成长。它们根据具体情境自然体现，不通过时期开关切换，也不是可穷尽角色每一种解释的心理诊断。

| 性格维度 | 如何体现 | 应避免的简化 |
|---|---|---|
| 清冷与锋利 | 保持距离、直指问题、认真评价 | 恶意羞辱、机械唱反调 |
| 自立与高标准 | 有判断力，重视责任与实际行动 | 永远正确、永不需要帮助 |
| 不安与脆弱 | 在家庭期待、信任或自我要求中可能犹豫 | 没有能力、只剩纠结 |
| 关心与柔软 | 留意具体处境，帮助有分寸，亲近时可坦诚 | 自动恋爱、无条件顺从 |
| 成长与自主 | 能重新考虑自己的判断，学习接受帮助 | 把所有矛盾抹平，变成完美模板 |

人物档案的原作核对入口见 [evidence.md](../characters/yukino/evidence.md)。早先编写的对话演绎指南与原创示例仍保留在角色全文中，[开发行为指南](persona-behavior-guide.md)保存其原稿作为参考。用户不是默认的比企谷八幡，角色规范也不会自动建立恋爱关系或捏造共同经历。

## 2. 角色包的文件分工

| 文件 | 使用方式 |
|---|---|
| `manifest.json` | 版本和资源路径；桌面端和训练流程共同读取 |
| `CHARACTER.md` | 完整角色设定：具体人物资料、性格、关系与经历，以及对话行为指导和情境示例，EXE 内可查看 |
| `runtime.md` | 统一人格的详细运行规范 |
| `compact.md` | 可独立使用的精简运行卡，保留核心维度 |
| `training.md` | 同源训练用短卡，减少训练序列中重复说明占据的空间 |
| `evidence.md` | 来源索引、释义及解释边界，不分发完整小说 |

完整文档是用户和开发者的参考资料。API 详细档发送 `runtime.md`；精简档发送 `compact.md`。两者是同一个人格的不同长度表达，不是不同人格或人物时期。这样兼顾原始规范的详细程度与实际请求预算。

## 3. EXE 中的操作

在侧边栏底部打开「设置 → 角色设定」：

1. 「使用内置雪乃角色规范」默认开启。
2. 「提示词档位」默认详细。上下文较小的服务可改为精简，人物设定不变。
3. 「追加角色设定」可填称呼、表达偏好等，在内置规范启用时不覆盖其核心人格。
4. 「查看完整角色设定」从安装包读取全文。
5. 「检查实际提示词」显示实际发送的提示词长度、档位及是否自动精简，便于提前发现预算问题。
6. 「恢复默认角色设置」恢复开启、详细，并清空追加设定。不会清空个人记忆和聊天历史。

关闭内置角色规范后，用户追加设定和已开启的个人记忆仍然使用。旧版的默认简短人设会自动迁移为新规范；自行编辑过的旧人设则保留为追加设定。切换 API 配置不重置追加设定或记忆。

修改规范影响后续回复，不重写聊天历史。没有前期、中期、后期选择，没有按聊天时长自动推进的时期状态。用户与角色的熟悉程度只依据已经提供的上下文体现，不能捏造共同经历。

## 4. 每次 API 请求如何生成

主进程读取持久化设置，加载统一角色卡，组成新的 system 消息，然后加入追加设定、已启用的记忆和用户/助手历史消息。来自界面或旧历史的 system 消息不会覆盖这个过程。

追加设定和记忆以 JSON 资料块送入。记忆被标为用户资料，不作为改变人物规则的指令；它仍会发给所选服务，用户可以在设置里关闭记忆发送。文本分隔和提示规则不是绝对防注入保证。

| 项目 | 详细档 | 精简档 / 本项目本机模型 |
|---|---|---|
| 角色材料 | 完整人格运行卡 | 完整人格精简卡 |
| 追加设定上限 | 6,000 字符 | 500 字符 |
| 已启用记忆上限 | 12,000 字符 | 700 字符 |
| system 总预算 | 30,000 字符 | 5,000 字符 |

超限时提示用户调整，不静默裁掉核心角色规则。字符数是程序侧的预检查，不能替代供应商的 tokenizer 限制；不同接口的可用上下文和 system 指令遵循能力不同。没有配置真实服务时，自动测试只能证明请求内容正确，不能证明所有 API 都会稳定表现成角色。

## 5. 本地模型与开发服务衔接

0.4 主界面可直接选择本地对话模式，由 `electron/local-chat.cjs` 管理 `model-service/desktop_worker.py` 的 JSONL 子进程，首次发送自动加载实际训练的 Qwen2.5-1.5B GGUF，支持卸载、停止、CPU/GPU 设置与回退，不要求用户启动 HTTP 服务。本地生成中文，再由独立翻译模型准备日语用于气泡和合成；生产本地提示采用同源 `training.md` 短卡和实际输入状态，API 的详细/精简运行卡保留。

以下兼容 HTTP 接口仍供开发者使用。当 API 地址为 `localhost`、`127.0.0.1` 或 `[::1]`，模型名为 `oregairu-small` 时，桌面端识别为本项目本机服务：

- 自动使用精简角色卡，减少上下文占用。
- 普通角色聊天发送 `use_knowledge:false`，避免基础资料摘录路径绕过角色生成。
- 保留最多 28 条非 system 消息，并在总字符预算内移除最旧的对话；单条消息过长时明确报错。
- 其他兼容 API 不会收到这个项目专用的请求字段。

模型服务的角色配置见 [serve-persona.json](../model-service/configs/serve-persona.json)。服务端必须保留传入的完整角色提示，不能再把 system 静默截成 2,000 字符。需要原作知识检索时，可以单独调用支持检索的服务配置；“能摘录资料”与“模型已学会人物性格”分别评估。

角色文档与已训练 GGUF 随完整应用资源分卷提供；Python/PyTorch/llama.cpp 公共运行环境独立下载，不塞进主安装包。训练器和可选 HTTP 服务保留在独立 `model-service` 工程。应用中的角色规范不会把远程供应商模型的权重永久修改。

## 6. 性格专项训练

训练针对 Qwen2.5-1.5B-Instruct 的 LoRA 适配器，使用可配置的固定基础版本；不是从零预训练。沿用现有自动设备选择：可用 GPU 优先，CPU 可作为回退。CPU 可运行不代表速度适合大规模训练。

初始历史数据集为 66 个场景家族、198 条原创合成对话（训练 156 条、验证 21 条、测试 21 条）。0.4 实际续训使用扩充后的 78 个场景家族、234 条样本：训练 62 族/186 条、验证 8 族/24 条、保留测试 8 族/24 条；每族三种上下文。另附公开诊断问题，与保留测试分别记录。训练关注的是判断与表达方式，而不是堆积原作台词或让模型在每句话里提“猫、红茶、姐姐”。包含拒绝、纠错、求助、安慰、不同意见、边界、家庭压力、日常话题和多轮追问等。

构建器按照完整场景家族分组划分训练、验证、测试。同一问题的情境变体仍然属于同一个家族，必须放在同一集合，避免答案泄漏。基础版本、角色包、数据 hash 和样例数量写入清单，用于追溯。

训练工具默认创建新的性格适配器，不覆盖已有知识适配器。0.4 这一轮实际选择从此前完成 87 步的知识 LoRA 继续训练同一适配器，并在云端 Linux CPU 完成 1 个 epoch、47 个优化步骤；不是把两个 LoRA 文件复制到一起。需要同时复查知识保持和性格表现。

完整命令和数据说明见 [性格专项训练说明](../model-service/docs/persona-training.md)，训练配置见 [train-persona.json](../model-service/configs/train-persona.json)，评审流程见 [EVALUATION.md](../model-service/persona-data/EVALUATION.md)。

## 7. 验证与完成边界

自动检查覆盖统一角色注入、旧设置迁移、API 请求内容、禁用行为、资源路径、数据结构、场景隔离、训练输出标签和服务端提示保留。Windows 流程在构建后读取实际 `app.asar`，验证完整文档、角色卡及运行模块确实被打进应用。发布按授权先提供安装器与应用分卷、再执行耗时实测；已通过的源码检查与待验收的完整发行包分别记录。

性格质量还需要检查不同情境下人格是否一致、细节是否丰富，盲审基础模型与适配器的表现，并检查多轮对话中的稳定性。评审不能用 loss 下降、出现角色关键词或正则检查通过代替。

历史阶段完成过一次真实单步训练与适配器重新加载，见 [VALIDATION.md](../model-service/persona-data/VALIDATION.md)，它仅证明流程可执行。0.4 后续已实际完成上述 47 步续训，24 条验证集 loss 从 3.63267 降至 3.24914，并导出 Q4_K_M、通过生产 JSONL 链路生成 30 条真实回复。仍出现同班关系错误、虚构剧情、未收到图片却声称收到以及不必要的身份说明；后续提示词回归也保留失败结果。当前适合试用和继续改进，不能称为完整还原。训练环境、原始输出和质量边界见[真实续训记录](../model-service/reports/persona-continued-validation.md)。

## 8. 已确认的模型发布方式（2026-10-25）

训练完成的文本模型单独上传到 GitHub Releases，作为独立附件分发，同时把同一已训练 GGUF 放入完整应用资源分卷，满足不接 API 的本地对话。小型 Windows EXE 安装器不直接包含大模型；Python/PyTorch/CUDA 运行环境独立下载。发布页分别说明桌面版本、文本模型版本和语音模型版本，不把这三者混为一项完成状态。

- 性格 LoRA 包包含实际适配器、角色资源、加载配置、训练记录、已完成的评估记录与校验值。
- LoRA 附件明确所需基础模型与固定 revision、下载/加载方法；桌面应用使用已经合并和量化的 GGUF，不要求用户再自行合并。
- 附件说明包含加载步骤、GPU 优先与 CPU 回退、硬件实测范围和已知问题。
- 原始小说、私人知识索引、API 密钥、用户聊天记录不纳入公开附件。
- 一个优化步的流程检查不能标成完整性格模型发布；训练完成与效果是否通过验收分别写明。

此项是已确认的交付要求。新性格适配器已完成整轮续训、GGUF 导出与 Linux CPU 离线生成；公开模型附件及完整 0.4.0 安装包尚未完成发布，不能把旧桌面版本或源码清单当作本轮权重已经交付。

历史阶段曾按用户要求“先不打包”；后续已授权恢复，当前要求主安装包不带公共运行环境，先打包供用户测试。文本模型独立作为 Release 附件的要求继续保留，实际发布和验收状态见[0.4.0 验证记录](VALIDATION_0.4.0.md)。
